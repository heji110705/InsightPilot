## 一、项目一句话（自我介绍 / 邮件正文可用）

> InsightPilot 是一个多智能体自助问数平台：业务同学用中文提问，六个 Agent 协作完成
> 「意图解析 → 语义层检索 → SQL 生成 → 安全执行 → 统计选图 → 自检」，
> 输出结论、图表和口径说明。我重点解决的是大模型写 SQL **不可信**的问题——
> 用语义层约束它、用 AST 沙箱兜住它、再用 60 题评测集证明它到底行不行。
> 最后这一步是重点：我不知道它有多准，直到我把"准"定义清楚并量出来。

## 二、AI 应用开发岗版（主推版）

**InsightPilot · 多智能体自助问数平台** ｜ 独立开发 ｜ 2026.11 – 至今
**技术栈**：Python 3.12 · FastAPI · Pydantic v2 · SSE · sqlglot · SQLite ·
自研 Agent 状态图引擎 · 手写 BM25 · MCP（JSON-RPC 2.0 over stdio）· OpenAI 兼容协议

- **多 Agent 编排**：手写状态图引擎（280 行，节点 / 条件边 / 检查点 / max_steps 保护），
  实现**执行失败回灌重试（≤3 次）与结论自检打回（≤2 次）两条反馈回路**；节点为纯函数
  `(State, Context) -> Patch`，路由外置于图定义，同一批节点可装配出 4 种策略配置，
  消融实验因此只是换装配代码、不改 Agent 一行。
- **语义层约束生成**：不把整库 DDL 塞进 prompt，而是构建 **8 张表卡片 + 20 条指标口径 +
  24 条范例 SQL** 三路召回：手写 BM25（中文 2-gram + 停用词表）+ 同义词扩展 + 两跳 JOIN
  补全 + token 预算裁剪（2600），每次召回带 `hit_reason` 可解释；并把行数 / 小数位 /
  最小样本量这类**输出约定外置到 `defaults.yml`**，可被测试断言，而不是靠提示词里一句软话。
- **可信输出设计**：统计、派生指标、极值趋势全部由代码计算，**模型只负责措辞**；
  措辞里的每个数字回查结果集（含千分位归一化与可重算派生值），查不到即丢弃该表述并回退
  规则结论——从机制上消除"编造数字"这一类幻觉。
- **安全与可观测**：sqlglot 解析 AST 后做单条 SELECT + 表名白名单 + CTE 豁免 + 强制行数上限，
  配合只读 URI 与 `PRAGMA query_only` 四层防护（54 个守卫用例：写操作 / ATTACH / PRAGMA /
  系统表 / 多语句 / 危险函数）；自建 trace 落 SQLite，记录每节点耗时与召回依据，
  并对外提供 SSE 节点级事件流与**手写 MCP 服务端**（267 行，3 个工具，零新增依赖），
  可被 Claude Desktop / Cursor 直接调用。
- **可评测（我认为最值钱的一条）**：60 题评测集（6 类各 10 题），**自己实现结果集等价判定**——
  列名不比、行序不比、1e-6 相对容差，另加一个**列覆盖判定**区分"答对了但多给列"；
  4 组消融 × **每组 2 轮**，并用重复性检验量化噪声（同配置波动 0–3.4pp）。
  结果：规则基线 **18.3%** → 模型 **50.0%**（列覆盖 **57.5%**）；单题 ¥0.005、p50 5.7s。
  **不声称多 Agent 带来提升**——组间极差 5pp，和重复波动同量级，n=2 撑不起因果。
- **工程完整性**：267 个测试（守卫 54 / 评测 44 / 语义检索 34 / Agent 31 / API 20 /
  编排 17 / 仓库 17 / MCP 15 / ETL 13 / trace 10 / 输出约定 12）、8500 行应用代码；
  `doctor.py` 六项自检、Makefile 与 `tasks.py` 双入口（Windows 无 make）、
  `.env.example` 全量环境变量、Dockerfile + compose（**本机无 Docker，构建未实测**，写在明面上）。

> **只能留 3 条**：留第 1、3、5 条。第 2 条技术含量最高但 30 秒讲不清；
> 第 4 条可以在被问到"怎么防注入"时展开。
> **如果岗位偏评测 / 数据质量**：把第 5 条提到第 1 位，第 6 条压成半句话。

## 三、数据岗版（投数据分析实习时替换第 1、2 条）

**InsightPilot · 语义层驱动的自助问数系统** ｜ 独立开发 ｜ 2026.11 – 至今

- **面向分析的重建模**：把毕设 Django 库（40+ 字段、命名无业务含义）重构为星型模型——
  3 张维度表 + 4 张事实表 + 1 张宽表视图，逐表标注 `grain`（一行代表什么）与口径陷阱，
  使"每个出版社平均评分"这类问题的字段歧义下降为 0。
- **口径治理**：建立 20 条指标口径目录（定义 / 公式 / 单位 / 陷阱 / 参数化 SQL 模板），
  把"评分是 0-10 分不是 1-5 星""点击表含 expose 事件"等易错点固化在配置里，
  避免同一指标在不同人口中出现两个数；输出约定（行数 / 小数位 / 最小样本量）单独成文件。
- **口径错误的实证**：按"4 星以上为好评"算出 99.7% 的好评率，据此反查发现源库评分实为
  0-10 分，修正后口径成立；同类问题另发现宽表视图因四表直连产生笛卡尔放大
  （真实计数 18/11/26/13 被放大为 66924）。
- **可量化的交付**：60 题评测集覆盖单表聚合 / 分组排序 / 多表关联 / 时间窗 / 比率 /
  口径陷阱六类，以结果集等价判定：规则基线 **18.3%**，接入模型后 **50.0%**（两轮均值，
  列覆盖 57.5%）；做了重复性检验，量化出同配置波动 **0–3.4 个百分点**，
  据此拒绝为小于该量级的消融差异下结论。
- **主动审计自家考卷**：逐题复核 60 题的题面与金标准，发现 8 题"问一本、给 5 行"的
  自相矛盾，修正后保留 v1 快照可复现旧分数（41.7% / 45.0% → 50.0%），
  并明确"审计只修不可能同时成立的矛盾，不把每道题调到模型答对为止"。

## 五、面试预案：18 个最可能被追问的点

### 架构类

**Q1 为什么不用 LangGraph？**

> 我需要讲清状态合并、条件边、检查点三件事，所以手写了一遍，280 行。
> 节点是纯函数，路由在图定义里，换成任何框架只是换装配代码，Agent 一行不改。
> 实际收益很具体：四个消融配置就是四份装配，不用给框架打补丁。

**Q2 六个 Agent 是不是过度设计？**

> 有两个是必需的：SchemaLinker（不给它，模型就在全库里瞎猜字段）和 Executor
> （安全边界必须独立于生成）。Critic 我保留，但要诚实说：**消融里没测出它的收益**。
> 两轮下来 no_critic 是 50.8%，full 是 50.0%，差 0.8 个百分点、不到一题，
> 在 0–3.4pp 的噪声带里，等于没差别。
> 它真正的价值不在 EX：60 题里它拦下并重写了若干"结论里的数字对不上结果集"的表述
> （trace 里能看到"已移除 N 条无法由结果集支撑的表述"）。它不改 SQL，所以对 EX
> 本来就不该有影响。**如果只能留两个 Agent，我留 Linker 和 Executor。**

**Q3 Agent 之间怎么通信？**

> 结构化对象，不是自然语言。`Intent → SQLContext → SQLDraft → ResultSet → Insight → Verdict`。
> 判据是：能用 schema 表达清楚的，就不要用自然语言传，否则每传一次就损耗一次。

**Q4 状态是怎么合并的？冲突怎么办？**

> 节点返回 patch，引擎合并到状态副本。覆盖一个已填字段是允许的（重试路径就是这么做的），
> 但会在 `notes` 里记 `overwrite:result`，事后看 trace 能还原"这个字段被改过几次、谁改的"。

### 效果类

**Q5 你的准确率是多少？**

> 60 题评测集，结果集等价判定：规则基线 **18.3%**，接入 DeepSeek-chat 后 **50.0%**
> （两轮都是 50.0%，列覆盖 57.5%）。提升 31.7 个百分点，这是整张表里唯一远超噪声的对比。
> 但我会主动补一句：**同一配置连跑两次会差 0–3.4 个百分点**，所以任何小于 3pp 的结论
> 我都不下。这不是谦虚，是我真做了重复实验才发现单次评测不可信。

**Q6 50% 是不是偏低？**

> 偏低，而且我知道低在哪。30 个失败里 28 个是"SQL 跑通了但结果不等价"：
> 18 个列数不同、8 个取值不同、2 个行数不同，另外 1 个被安全策略拒绝、1 个走了澄清。
> 按题型看，T1 单表聚合 90%、T2 分组排序 70%、T3 多表 60%、T4 时间窗 50%，
> 塌在 T5 比率 20% 和 T6 口径陷阱 10%。
>
> 这里的坑我踩过：一开始我把"26 个列数不同"当成主要病因，写进 README 说
> "是模型多给了列、一条提示词就能收"。后来加了列覆盖判定才发现只有 **4 题**是
> 纯粹多给列，其余都伴随取值或粒度错误，**10 题反而是少给了列**。
> 症状当病因，差点写出一条错误的优化结论——这个过程我留在开发纪实里了。

**Q7 消融结果说明多 Agent 有用吗？**

> 老实说：**不能用这张表证明多 Agent 有用**。
> 两轮均值：full 50.0%、no_critic 50.8%、no_schema 45.0%、single 45.0%；
> 组间极差 5 个百分点，而同配置重复波动就有 3.4 个百分点，每配置只跑了 2 次。
> 能说的只有两句：去掉语义层检索掉 5 个点、退化成单 Agent 掉 5 个点，方向符合预期
> 但不显著；**去掉 Critic 反而高 0.8 个点**，在噪声内。
>
> 还有个反直觉的发现：**列覆盖四组几乎持平**（57.5 / 56.7 / 57.5 / 57.5）。
> 也就是说多 Agent 的差异主要在"投影收没收住"，不在"信息对不对"。
> 我不会把它写成"多 Agent 带来提升"，那样经不起一句"你跑了几次"。

### 数据与正确性类

**Q8 怎么保证模型不编数字？**

> 三道关：一是统计全部由代码算，模型只写措辞；二是措辞里的数字回查结果集，
> 千分位先归一化，可重算的派生值（合计 / 均值 / 极差）也算合法；三是 Critic 兜底，
> 查不到就丢弃这段表述。
> 有个反例很能说明问题：我一开始校验太严，把自己算的"合计 5001"也判成编造，
> 结果自检把正确结论毙了——后来才补上"可重算派生值"这一类。

**Q9 SQL 注入怎么防？**

> 四层：sqlglot 解析 AST 后判定根节点必须是单条 SELECT（不是正则匹配文本，正则必被绕过）、
> 表白名单、只读 URI 打开、`PRAGMA query_only=ON`。
> 另外拦了 `ATTACH` / `PRAGMA writable_schema` / 读 `sqlite_master` / 多语句拼接，
> 以及 `load_extension`、`readfile` 这类只读连接挡不住的危险函数。
> 守卫用例 54 个，分类覆盖写操作、ATTACH、PRAGMA、系统表、多语句、危险函数。

**Q10 结果集等价怎么判？**

> 列数相同、列名不比（别名不同但结果对就是对的）、行序不比（转 multiset）、
> 数值容差 `max(1e-6, 1e-6·|a|)`、None 与空串不等、字符串去首尾空白但大小写敏感。
> 32 个用例压这个判定，因为这里最容易做出一个"看起来很严格其实很松"的东西。
>
> 后来我又加了一个**列覆盖判定**：允许预测多带列，只要金标准的每一列都能按值
> 映射到一个预测列（贪心 + 回溯找映射），映射完再重新投影比对一次，防止行错位。
> 两个指标并列报：EX 50.0% / 覆盖 57.5%。差的那 7.5 个点就是"答对了但投影没收敛"。

**Q11 267 个测试都测什么？**

> 按风险排序，不是按覆盖率。守卫 54（安全不能漏）、评测 44（判定错了整个实验白做）、
> 语义检索 34（召回错了后面全错）、Agent 31（我手写的部分）、API 20、编排 17、
> 仓库 17、MCP 15、ETL 13、trace 10、输出约定 12。
> 其中特意留了几条"结构守卫"：报告的自然语言结论必须随模式切换、章节号必须连号
> ——这类测试防的不是 bug，是我自己改文档时的手滑。

### 工程类

**Q12 为什么图表服务端出 SVG？**

> 前端零 CDN 依赖。ECharts 走 CDN，网络抖一下演示就白屏，这个风险不值得冒。
> 而且"不引图表库也能把 bar/line/pie 画对"本身是个判断——什么时候该引库，什么时候不该。

**Q13 数据量多大？能扛住生产吗？**

> 万级事实表（250 书 / 4202 评分 / 9028 点击 / 1976 评论 / 2532 书架），单机 SQLite，
> **不能**扛生产，我在 README 的能力边界里写清了。
> 放大 100 倍先崩三处：维度值全量进内存、SQLite 单写、全表 GROUP BY。
> 这三处都在 `Repo` / `Retriever` 接口后面，换 DuckDB 或 Postgres 不会扩散到 Agent 层。

**Q14 MCP 为什么手写，不用官方 SDK？**

> 协议核心就四个方法（initialize / tools/list / tools/call / 通知），自己实现 267 行，
> 零新增依赖——这个项目卖点之一是"pip install 完就能跑"，多一条会版本漂移的依赖
> 就多一个装不上的理由。
> 手写还守住了三件容易被忽略的事：stdout 只能有 JSON-RPC（日志必须走 stderr，
> 否则客户端解析直接崩）、通知不能回响应、错误要分两层（协议级 JSON-RPC error 与
> 工具级 `result.isError`）。这三条都有子进程级测试盯着。

### 软性类

**Q15 这个项目最难的地方是什么？**

> 不是 Agent，是**判定标准**。写一个能跑的 Agent 一周就够，
> 但"怎么证明它变好了"要想很久：比 SQL 字符串？比结果集？列名算不算？行序算不算？
> 多给一列算不算错？我最后给了两个指标并列，因为"哪种算对"本身取决于使用者
> 是要核对数字还是要一个能贴进报表的表。

**Q16 你从中学到什么？**

> 两条。第一条：**别相信"测试通过"**。视图笛卡尔放大那个 bug，250 行断言全绿，
> 但每个计数都是乘积。从那以后我给"看起来对"的数字都加一道独立校验。
> 第二条：**指标决定了你能看见什么**。只有严格 EX 时，我看不见"多给一列"和"算错"
> 的区别，于是把症状当成了病因；加了覆盖判定，30 个失败才裂成 4 + 26。
> 观测手段不足的时候，你连自己的错误都看不见。

**Q17 如果继续做，下一步做什么？**

> 按优先级：① T5/T6 专项——比率和口径陷阱合计只有 3/20，值得单独做一轮 30 题；
> ② 口径单测——每个指标配一条断言 SQL，口径改错立刻红，而不是等人肉发现；
> ③ 多轮上下文补强（现在只做指代消解，不做跨会话）；
> ④ Docker 构建实测（文件已就绪，本机没装 Docker）。
>
> 有一件我**故意没做**：把评测集拆成 dev/test。40/20 的话，test 上每题权重 5 个百分点，
> 比 3.4pp 的噪声带还大，统计功效反而下降——现在拆是自欺欺人，等题量上百再说。

**Q18 你简历上这个 50% 会不会太低，别人都写 90%？**

> 那两个数不可比，因为判定的严格程度不同。我把列名、行序都放开，已经是在往"宽松"
> 的方向让步了；但如果对方比的是"答案里包含正确信息"，那我的覆盖一致是 57.5%；
> 如果比的是"人工看一眼觉得对"，可能还会更高。
> 我能保证的是：**这个 50% 是 60 道题、两轮、可复现、代码在仓库里跑出来的**，
> 换个人拉下来跑一遍还是这个数。别人那 90% 怎么算的，我不知道，所以我不写。

## 七、投递时的用法建议

1. **AI 应用开发岗**：用第二节的前 4 条 + 第 5 条（评测），排在项目经历第一位——
   它比图书推荐更贴岗，而且"我自己定义并度量了准确率"这件事，比多写两个功能更能说明问题。
2. **数据分析岗**：用第三节，重点在"重建模 + 口径治理 + 审计自家考卷"，弱化编排细节。
3. **面试前 10 分钟**：只看 Q1 / Q5 / Q6 / Q7 四问。Q6 和 Q7 是最容易被追问到崩的
   ——因为它们的正确答案都是"我不知道 / 不能证明"。
4. **带电脑去面试**：`python scripts/doctor.py` 先自检，再
   `python -m uvicorn app.api.server:app` 一行起来，现场让他随便问一句。
   比任何描述都有说服力。**前提是你自己先跑过 20 遍**，包括没网的时候（规则基线兜底）。
