## 一、项目一句话（自我介绍/邮件正文可用）

> InsightPilot 是一个多智能体自助问数平台：业务同学用中文提问，六个 Agent 协作完成  
> 「意图解析 → 语义层检索 → SQL 生成 → 安全执行 → 统计选图 → 自检」，  
> 输出结论、图表和口径说明。我重点解决的是大模型写 SQL **不可信**的问题——  
> 用语义层约束它、用 AST 沙箱兜住它、用 60 题评测集证明它到底行不行。

## 二、AI 应用开发岗版（主推版，建议 4 条）

**InsightPilot · 多智能体自助问数平台** ｜ 独立开发 ｜ 2026.11 – 至今  
**技术栈**：Python 3.12 · FastAPI · Pydantic v2 · SSE · sqlglot · SQLite · 自研 Agent 状态图引擎 · OpenAI 兼容协议

- **多 Agent 编排**：手写状态图引擎（节点 / 条件边 / 检查点 / max_steps 保护，约 270 行），实现  
  **执行失败回灌重试（≤3 次）与结论自检打回（≤2 次）两条反馈回路**；节点为纯函数  
  `(State, Context) -> Patch`，路由外置于图定义，同一批节点可装配出 4 种策略配置。
- **语义层约束生成**：不自建"整库 DDL 塞 prompt"，而是构建指标口径目录（20 个指标）+ 表卡片（8 张）
  - 范例 SQL（24 条）三路召回，手写 BM25 与同义词扩展，每次召回带 `hit_reason` 可解释；  
    按 token 预算裁剪（2600）并保留 join 二跳，保证多表路径可达。
- **可信输出设计**：统计、派生指标、极值趋势全部由代码计算，**模型只负责措辞**；  
  措辞中的每个数字回查结果集（含千分位归一化与可重算派生值），查不到即丢弃其表述并回退规则结论，  
  从机制上消除"编造数字"这一类幻觉。
- **安全与可观测**：sqlglot 解析 AST 后做单条 SELECT 白名单 + 表名白名单 + CTE 豁免 + 强制行数上限，  
  配合只读 URI 与 `PRAGMA query_only` 四层防护（含 54 条攻击样例测试）；  
  自建 trace 落 SQLite，记录每个节点的耗时/状态/召回依据，并提供树形回放页与 SSE 节点级事件流。
- **工程完整性**：219 个测试用例（编排 16 / 守卫 54 / 仓库 17 / 检索 34 / Agent 31 / API 20 / 评测 23 / ETL 13），  
  端到端 p50 140 ms；60 题评测集采用**结果集等价**判定（列名无关、行序无关、数值容差），  
  并实现 full / no_critic / no_schema / single 四组消融。

> 如果只能留 3 条：留第 1、3、4 条。第 2 条是技术含量最高但最不好在 30 秒内讲清的。

## 三、数据岗版（投数据分析实习时替换第 1、2 条）

**InsightPilot · 语义层驱动的自助问数系统** ｜ 独立开发 ｜ 2026.11 – 至今

- **面向分析的重建模**：把毕设 Django 库（40+ 字段、命名无业务含义）重构为星型模型——  
  3 张维度表 + 4 张事实表 + 1 张宽表视图，逐表标注 `grain`（一行代表什么）与口径陷阱，  
  使"每个出版社平均评分"这类问题的字段歧义下降为 0。
- **口径治理**：建立 20 条指标口径目录（定义 / 公式 / 单位 / 陷阱 / 参数化 SQL 模板），  
  把"评分是 0-10 分不是 1-5 星""点击表含 expose 事件"等易错点固化在配置里，  
  避免同一指标在不同人口中出现两个数。
- **口径错误的实证**：按"4 星以上为好评"计算得出 99.7% 的好评率，据此反查发现源库评分实为 0-10 分，  
  修正后口径成立；同类问题另发现宽表视图因四表直连产生笛卡尔放大（真实计数 18/11/26/13 被放大为 66924）。
- **可量化的交付**：60 题评测集覆盖单表聚合 / 分组排序 / 多表关联 / 时间窗 / 比率 / 口径陷阱六类，  
  以结果集等价判定准确率：规则基线 18.3%，接入模型后 43.3%（两轮均值，单轮 41.7% / 45.0%）；  
  并做了重复性检验，量化出同配置波动 3.3 个百分点，据此拒绝为小于该量级的消融差异下结论。

## 五、面试预案：16 个最可能被追问的点

### 架构类

**Q1 为什么不用 LangGraph？**

> 我需要讲清状态合并、条件边、检查点三件事，所以手写了一遍，约 270 行。  
> 节点是纯函数，路由在图定义里，所以换成任何框架只是换装配代码，Agent 一行不改。  
> 实际收益是：三个消融配置就是三份装配，不用给框架打补丁。

**Q2 六个 Agent 是不是过度设计？**

> 有两个是必需的：SchemaLinker（不给它，模型就在全库里瞎猜字段）和 Executor（安全边界必须独立）。  
> Critic 我保留，但要诚实说：**消融里没测出它的收益**。两轮下来 no_critic 是 44.2%，  
> full 是 43.3%，差 0.9 个点，在 3.3 个点的噪声带里，等于没差别。  
> 它现在的作用是拦"结论里的数字对不上结果集"——这个在结论层确实拦到了（60 题里 4~6 次触发回退重写），  
> 但它不改 SQL，所以对 EX 本来就不该有影响。我留着它是因为答错代价高于答慢代价，不是因为数据证明它有用。  
> **如果只能留两个 Agent，我留 Linker 和 Executor。**

**Q3 Agent 之间怎么通信？**

> 结构化对象，不是自然语言。`Intent → SQLContext → SQLDraft → ResultSet → Insight → Verdict`。  
> 判据是：能用 schema 表达清楚的，就不要用自然语言传，否则每传一次就损耗一次。

**Q4 状态是怎么合并的？冲突怎么办？**

> 节点返回 patch，引擎合并到状态副本。覆盖一个已填字段是允许的（重试路径就是这么做的），  
> 但会在 `notes` 里记 `overwrite:result`，事后看 trace 能还原"这个字段被改过几次、谁改的"。

### 效果类

**Q5 你的准确率是多少？**

> 60 题评测集，结果集等价判定：规则基线 18.3%，接入 DeepSeek 后 43.3%  
> （两轮均值，单轮 41.7% / 45.0%）。提升 25 个百分点。  
> 但我会主动补一句：**同一配置连跑两次差 3.3 个百分点**，所以任何小于 3pp 的结论我都不下。  
> 这不是谦虚，是我真的做了重复实验才发现单次评测不可信。

**Q6 43% 是不是偏低？**

> 偏低，而且我知道低在哪。35 个失败里 26 个是"列数不同"——模型多给了没被问到的列，  
> 比如问"整体好评率"，它把评分总数、好评数也一起 SELECT 出来。  
> 这类失败不是"算错了"，是"输出投影没收住"，对应一条提示词规则就能改，  
> 说明这个 43% 里有相当一部分是**我提示词的锅，不是模型能力的上限**。  
> 另外 T6（口径陷阱）10 题全灭，因为题目本身刻意含糊，gold 选了一个明确口径，  
> 而我要求模型含糊时先反问——这是设计选择带来的必然扣分，我接受。

**Q7 消融结果（43.3 / 44.2 / 39.2 / 39.2），说明多 Agent 有用吗？**

> 老实说：**不能用这张表证明多 Agent 有用**。  
> 两轮均值是 full 43.3%、no_critic 44.2%、no_schema 39.2%、single 39.2%，  
> 组间极差 5 个百分点，而同配置重复波动就有 3.3 个百分点，每配置只跑了 2 次。  
> 能说的只有两句：去掉语义层检索掉 4 个点、退化成单 Agent 掉 4 个点，方向符合预期但不显著；  
> **去掉 Critic 反而高 0.9 个点**，在噪声内，等于这个模块没测出收益。  
> 我不会把 43.3 写成"多 Agent 带来提升"，那样经不起追问。

### 数据与正确性类

**Q8 怎么保证模型不编数字？**

> 三道关：一是统计全部由代码算，模型只写措辞；二是措辞里的数字回查结果集，  
> 千分位先归一化，可重算的派生值（合计/均值/极差）也算合法；三是 Critic 兜底，查不到就丢弃这段表述。  
> 有个反例很能说明问题：我一开始校验太严，把自己算的"合计 5001"也判成编造，  
> 结果自检把正确结论毙了——后来才补上"可重算派生值"这一类。

**Q9 SQL 注入怎么防？**

> 四层：sqlglot 解析 AST 后判定根节点必须是单条 SELECT（不是正则匹配文本，正则必被绕过）、  
> 表白名单、只读 URI 打开、`PRAGMA query_only=ON`。  
> 另外拦了 `load_extension`、`readfile` 这类只读连接挡不住的危险函数。  
> 54 条攻击样例，包括 `SELECT 1; DROP TABLE`、子查询夹带非法表、UNION 分支夹带。

**Q10 结果集等价怎么判？**

> 列数相同、列名不比（别名不同但结果对就是对的）、行序不比（转 multiset）、  
> |  |  |  |  
> | --- | --- | --- |  
> 数值容差 max(1e-6, 1e-6·|a|)、None 与空串不等。  
> 33 个边界用例，因为这里最容易做出一个"看起来很严格其实很松"的判定。

### 工程类

**Q11 219 个测试都测什么？**

> 按风险排序，不是按覆盖率。守卫 54 个（安全不能漏）、检索 34 个（召回错了后面全错）、  
> Agent 31 个（我手写的部分）、评测 23 个（判定错了整个实验白做）。  
> 数据 ETL 只有 13 个，但其中一个是行数对账——它抓出过视图笛卡尔放大那种"测试全绿数字全错"的 bug。

**Q12 为什么图表服务端出 SVG？**

> 前端零 CDN 依赖。ECharts 走 CDN，网络抖一下演示就白屏，这个风险不值得冒。  
> 而且"不引图表库也能把 bar/line/pie 画对"本身是个判断——什么时候该引库，什么时候不该。

**Q13 数据量多大？能扛住生产吗？**

> 万级事实表，单机 SQLite，**不能**扛生产。我在 README 的能力边界里写清了。  
> 放大 100 倍先崩三处：维度值全量进内存、SQLite 单写、全表 GROUP BY。  
> 这三处都在 `Repo` / `Retriever` 接口后面，换 DuckDB 或 Postgres 不会扩散到 Agent 层。

### 软性类

**Q14 这个项目最难的地方是什么？**

> 不是 Agent，是**判定标准**。写一个能跑的 Agent 一周就够，  
> 但"怎么证明它变好了"要想很久：比 SQL 字符串？比结果集？列名算不算？行序算不算？  
> 我最后选了结果集等价，然后写了 33 个测试来保证这个判定本身是对的。

**Q15 你从中学到什么？**

> 一条：**别相信"测试通过"**。视图笛卡尔放大那个 bug，250 行的断言全绿，但每个计数都是乘积。  
> 从那以后我给"看起来对"的数字都加了一道独立校验——比如好频率 99.7%，我第一反应不是"业务真好"。

**Q16 如果继续做，下一步做什么？**

> 三件事，按优先级：① 配 Key 跑出模型模式真实数字，把消融表补齐；  
> ② 评测集拆 dev/test，避免调规则时把 test 也调了；③ 加"口径单测"——  
> 每个指标配一条断言 SQL，口径改错立刻红，而不是等人肉发现。

## 七、投递时的用法建议

1. **AI 应用开发岗**：用第二版 4 条，把它排在项目经历第一位（它比图书推荐更贴岗）。

   现场让他随便问一句——这比任何描述都有说服力。**前提是你自己先跑过 20 遍。**
