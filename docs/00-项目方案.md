# InsightPilot · 多智能体自助问数分析平台
## 项目方案与实施计划（待确认稿 v1）

> 目标：从零构建一个**与「知行旅游助手（LangGraph 多 Agent）」同等甚至更硬的工程作品**，
> 可运行、可演示、可评测、可写进简历、可在面试中被追问 30 分钟不露底。

---

## 一、先说清楚：为什么不做「旅游助手 2.0」

舍友那个项目的技术骨架是：`LangGraph 多 Agent 编排 + 四阶段 RAG + MCP 工具接入 + 长短期记忆 + SSE 流式`。
这套骨架的价值不在"用了 LangGraph"，而在**把一个开放域任务拆成了多个可验证的子步骤**。

如果我们照做一个"多 Agent 旅行/学习/健身助手"，会有三个硬伤：

1. **撞车**：同一学院、同一届、同一位老师，两个几乎同构的多 Agent 对话系统，一眼就能看出出处。
2. **无差异化**：多 Agent + RAG 的旅游助手已经是烂大街的入门项目，面试官见过几十份。
3. **丢了你的底牌**：你是数据科学与大数据技术专业，手上有真实的豆瓣 Top250、250 本书、4202 条评分、**9028 条点击日志**。把这些扔掉去做旅游攻略，等于自废武功。

所以本项目换一个赛道，但**技术难度只升不降**：

| 维度 | 知行旅游助手 | InsightPilot（本项目） | 谁的难度更高 |
|---|---|---|---|
| 多 Agent 编排 | Handoffs/Router/Subagents 三模式 | 6 节点状态图 + 条件边 + 重试环 + 打回环 | 本项目（有反馈闭环） |
| 检索 | 四阶段 RAG（查询优化/混合/重排/父文档） | 语义层检索（schema card + 指标目录 + few-shot SQL 三路召回） | 相当（本项目召回目标更结构化，评估更硬） |
| 正确性验证 | 无量化评测（"能跑通"） | **执行准确率评测集 + 消融实验** | **本项目（这是最大差异）** |
| 安全边界 | 无 | AST 级 SQL 白名单 + 只读沙箱 + 限额超时 | 本项目 |
| 观测 | LangSmith（现成服务） | 自研 trace 落库 + 树形可视化 | 相当（自研更能讲清原理） |
| 数据 | 外部 API + 攻略文档 | **你自己写的两个项目产出的真实库** | 本项目 |

一句话定位差异：**他做的是"能跑的多 Agent"，本项目做的是"能被量化证明有效的多 Agent"。**

## 二、项目定位

**一句话**：面向中小内容/电商团队的**自助问数分析平台**——业务同学用中文提问，系统自动完成
`理解意图 → 定位数据 → 写 SQL → 安全执行 → 统计与选图 → 给出结论与口径说明`，
全过程可追溯、可评测、有安全边界。

**解决的真实问题**：业务方要一个数，得找数据分析师排期；分析师 80% 的时间花在"理解口径 + 写重复 SQL"上。
LLM 直接写 SQL 的问题是**不可信**（编字段、漏口径、算错比率、跑出全表扫描）。
本项目的解法不是"把 prompt 调好"，而是：

> **把不确定性从 prompt 挪到可维护的结构上** —— 用「语义层」（指标口径目录 + 表卡片 + 范例 SQL）约束模型，
> 用「Critic 自检」验证结论，用「评测集」证明有效，用「安全沙箱」兜住风险。

**核心命题（面试时的中心句）**：
> 我不相信"大模型能写 SQL"这件事，我只相信"在受约束的语义层上，大模型写 SQL 的执行准确率能从 X% 提到 Y%"。
> 所以这个项目的重心不在模型，在**约束**和**度量**。

**技术栈**：Python 3.12 · FastAPI · SQLite（只读仓库快照）· sqlglot · pandas · 自研 Agent Harness
（可选 LangGraph 后端）· Pydantic v2 · 原生 HTML/JS（无构建）· 服务端 SVG 图表 · pytest

## 三、架构设计

```
┌──────────────────────────── 用户提问（中文，支持多轮指代） ────────────────────────────┐
│                                                                                      │
│  ┌──────────┐   ┌───────────────┐   ┌──────────┐   ┌───────────┐   ┌──────────┐      │
│  │ ①Intake  │──▶│ ②SchemaLinker │──▶│ ③SQLCraft│──▶│ ④Executor │──▶│ ⑤Analyst │      │
│  │ 意图/澄清 │   │ 语义层检索     │   │ 生成 SQL │   │ 校验/执行 │   │ 统计/选图 │      │
│  └──────────┘   └───────────────┘   └──────────┘   └───────────┘   └────┬─────┘      │
│       │                                    ▲              │              │            │
│       │ 需要澄清                            │ 报错回灌重试  │              ▼            │
│       ▼                                    └──────────────┘        ┌──────────┐       │
│  ┌──────────────┐                                                  │ ⑥Critic  │       │
│  │ 回问用户（HITL）│                                                │ 结论自检  │       │
│  └──────────────┘                                                  └────┬─────┘       │
│                                                         不通过 → 打回 ⑤ │ 通过         │
│                                                          ┌───────────────┘             │
│                                                          ▼                           │
│                                              ┌────────────────────────┐              │
│                                              │ 结构化答复 + 口径脚注    │              │
│                                              │ SQL / 表格 / 图表 / CSV │              │
│                                              └────────────────────────┘              │
└──────────────────────────────────────────────────────────────────────────────────────┘
         每个节点 = 一个 Agent，输入输出都是 Pydantic 模型，全部落 trace span
```

**分层**（这是简历上要写的结构，也是面试被问"分层怎么切的"时的答案）：

| 层 | 内容 | 关键设计 |
|---|---|---|
| L1 接入层 | FastAPI 路由、SSE 事件流、静态页 | 事件粒度是"节点级"（start/end/error），不是 token 级 |
| L2 编排层 | 状态图引擎：节点注册、条件边、检查点、重试计数 | 状态是 Pydantic 对象，每节点进出都校验；检查点落 SQLite 可恢复 |
| L3 Agent 层 | 6 个 Agent，纯函数 `(State) -> StatePatch` | 无副作用、可单测、可替换 LLM Provider |
| L4 语义层 | 指标目录 / 表卡片 / 范例 SQL / 同义词别名 | **本项目的心脏**，也是和"裸 prompt 写 SQL"的分水岭 |
| L5 执行层 | sqlglot AST 校验 + 只读沙箱 + LIMIT/超时/行数上限 | 拒绝一切非单条 SELECT；`PRAGMA query_only` 双保险 |
| L6 数据层 | 星型模型仓库快照（dim_* / fact_*）+ 字典表 | 由 ETL 从你的 Django 库转出，只读 |

## 四、技术选型与「为什么不用 X」

面试必问，所以先想清楚：

| 决策 | 选型 | 理由 | 放弃了什么，为什么 |
|---|---|---|---|
| 数据库 | **SQLite 单文件快照** | 一键起、零运维、可进仓库、只读打开安全 | 放弃 MySQL/PG：不该让面试官装库才能看 demo；且数据量仅万级 |
| 数据模型 | **星型模型**（dim_book / fact_rating / fact_comment / fact_click / fact_shelf） | 分析型 schema 让 Text-to-SQL 的歧义大幅下降；同时展示建模能力 | 放弃直接查 Django 的 `books_book`：字段 40+、命名杂乱，模型极易选错列 |
| 语义层检索 | **自研 BM25 + 别名词典 + 结构加权** | 卡片量 <200，BM25 足够且**完全可解释**（能说清为什么召回这张卡） | 放弃向量库：Chroma 要装、要下模型、召回不可解释，收益不抵成本；接口留了 `VectorRetriever` 可插 |
| SQL 校验 | **sqlglot 解析 AST 后白名单校验** | 正则黑名单必被绕过（注释、大小写、函数嵌套）；AST 是唯一可靠方式 | 放弃正则；放弃 `sqlparse`（只分词不校验语义） |
| 编排 | **自研状态图 Harness**，同批节点函数可切 LangGraph 后端 | 手写一遍才知道 StateGraph 的本质（状态合并/条件边/检查点）；且零版本风险 | 放弃"直接用 LangGraph"作为唯一实现：版本漂移 + 黑盒，且和舍友项目同质化 |
| LLM | **Provider 抽象**：OpenAI 兼容（DeepSeek/Qwen/GLM 任一）+ **离线 Stub** | 没有 key 也能跑通全链路、跑评测、给面试官演示 | 放弃绑定单一厂商 SDK：换 key 就要改代码是设计缺陷 |
| 观测 | **自研 trace 落 SQLite + 树形可视化页** | 不依赖 LangSmith（要 key、要联网），且能讲清 span 埋点原理 | 放弃 LangSmith；保留 `LangSmithExporter` 接口占位（不实现，不吹） |
| 前端 | **原生 HTML/JS 单页，无构建** | 面试官 `python -m app` 就能开，不需要 node | 放弃 React/Vite：构建链对"看 demo"是负资产 |
| 图表 | **服务端渲染 SVG**（自写极简 bar/line/pie） | 离线可用，不依赖 CDN；且"不引 ECharts 也能出图"本身是工程判断 | 放弃 ECharts CDN：断网即白屏，演示事故高发 |

## 五、核心功能（8 项，每条都要能演示）

1. **中文问数 → SQL**：单轮 + 多轮，支持指代（"再按出版社拆一下"沿用上一轮的时间窗与过滤条件）。
2. **歧义澄清**：识别"最近/最好/热门/高评分"等口径模糊词；策略是**显式采用默认口径并标注**，只有致命歧义（涉及不同表）才回问用户。
3. **语义层三路召回**：表卡片（结构）+ 指标目录（口径定义与 SQL 模板）+ 范例 SQL（few-shot），合并去重后按 token 预算裁剪。
4. **自修复重试**：执行报错 → 错误信息 + 原 SQL + 相关表卡片回灌给 SQLCraft，最多 3 次，每次记 trace。
5. **安全执行沙箱**：单条 SELECT 白名单、禁 DDL/DML/ATTACH/PRAGMA、表名白名单、强制补 LIMIT、只读连接、2s 超时、5000 行上限。
6. **结果解读**：自动判型（单值 / 分组对比 / 时间序列 / 占比 / 明细），据此选图并生成结论句；结论必须绑定具体数字。
7. **Critic 自检**：三查——结论是否被结果集支持（数字对不上就打回）、样本量是否足够（<30 条要显式提示）、是否遗漏口径脚注。
8. **可观测与性价比**：全链路 trace（节点耗时/重试次数/SQL/行数）、会话记忆、语义缓存（同问同库直接命中，报告命中率）。

**附加能力（拉开差距用）**：
- `/eval` 评测页：跑评测集，展示执行准确率、首答正确率、平均重试次数、p50/p95 延迟、缓存命中率。
- **消融开关**：`--config single|no_schema|no_critic|full`，产出对比表。**这张表就是简历上最硬的一行。**

## 六、多 Agent 角色分工

| # | Agent | 职责 | 输入 → 输出 | 降级策略 |
|---|---|---|---|---|
| ① | **Intake**（意图与澄清） | 分类：问数 / 追问 / 寒暄 / 超范围；抽取时间窗、实体、指标词；检测歧义 | 问题 + 会话历史 → `Intent{type, entities, ambiguities, defaults}` | LLM 不可用 → 关键词规则 + 正则兜底 |
| ② | **SchemaLinker**（语义层检索） | 从指标目录/表卡片/范例 SQL 三路召回，二跳扩展关联表，按预算裁剪 | `Intent` → `Context{tables, columns, metrics, examples, join_hints}` | 召不回 → 退化为全量表卡片摘要（有 token 上限） |
| ③ | **SQLCraft**（SQL 工程师） | 依据 `Context` 生成单条 SELECT；遵守方言与口径；被重试时消费错误信息修订 | `Context + 上轮错误` → `SQLDraft{sql, rationale, used_tables}` | 连续 3 次失败 → 输出"无法可靠回答"+ 缺口说明 |
| ④ | **Executor**（执行与守卫） | AST 校验 → 补 LIMIT → 只读执行 → 结果集规整（列类型推断、空值处理） | `SQLDraft` → `ResultSet{columns, rows, rowcount, elapsed_ms}` 或 `SQLError` | 校验失败 → 返回结构化拒绝原因（不是异常栈） |
| ⑤ | **Analyst**（统计分析） | 判型 → 计算派生指标（占比/环比/累计）→ 选图 → 写结论句 + 口径脚注 | `ResultSet` → `Insight{shape, chart, bullets, footnotes}` | 结果为 0 行 → 明确说"该条件下无数据"，不编 |
| ⑥ | **Critic**（质量守门） | 三查：数字一致性 / 样本量 / 口径完整性；不通过给出具体打回理由 | `Insight + ResultSet + SQL` → `Verdict{pass, reasons}` | 打回 1 次仍不通过 → 降级输出但仍标注风险 |

**协作流程（图的边）**：
```
Intake ─(需澄清)─▶ 回问用户（HITL，等待补充后重入 Intake）
       └(可直接答)─▶ SchemaLinker ─▶ SQLCraft ─▶ Executor
                                          ▲          │(报错且 retry<3)
                                          └──────────┘
                                                     │(成功)
                                                     ▼
                                                  Analyst ─▶ Critic
                                                       ▲        │(不通过且打回<2)
                                                       └────────┘
                                                                │(通过)
                                                                ▼
                                                          Reporter 汇总输出
```
- **状态合并**：每个节点返回 `StatePatch`，引擎按字段浅合并，冲突即报错（避免"后写的覆盖先写的"这种隐蔽 bug）。
- **检查点**：每节点结束写一条 `checkpoint(turn_id, seq, state_json)`，中途崩了可从最近检查点重放。
- **并发**：单轮内串行（依赖强），但**评测集可并发跑**（每轮独立 session）。

## 八、评测设计（本项目最值钱的部分）

**评测集**：60 题，6 类各 10 题，人工写标准 SQL 并执行取真值。

| 类型 | 示例 | 考察点 |
|---|---|---|
| T1 单表聚合 | "一共有多少本书" | 基础计数、去重 |
| T2 分组排序 | "评分最高的 5 本书" | GROUP BY + ORDER + LIMIT，注意评分样本量 |
| T3 多表关联 | "每个出版社的平均评分和评论数" | JOIN 路径、1:N 聚合放大陷阱 |
| T4 时间窗 | "上个月每天的点击量" | 日期函数、边界含不含当天 |
| T5 比率类 | "各分类的评论转化率" | 分子分母口径、除零 |
| T6 口径陷阱 | "最受欢迎的书" | 歧义处理：点击量？评分人数？收藏数？ |

**指标**：
- **EX（执行准确率）**：生成 SQL 的**结果集**与标准 SQL 结果集等价（列名无关、行序无关、数值容差 1e-6）。**不做字符串比对**——这是专业与业余的分界线。
- **首答正确率**：不做重试时的正确率（衡量一次成型能力）。
- **平均重试次数**、**p50/p95 端到端延迟**、**缓存命中率**、**token 消耗**。

**消融实验（产出一张表）**：

| 配置 | EX | 首答正确率 | 平均重试 | 备注 |
|---|---|---|---|---|
| single（单 Agent 一把梭） | ? | ? | — | 基线 |
| no_schema（去掉语义层召回） | ? | ? | ? | 证明语义层的价值 |
| no_critic（去掉自检） | ? | ? | ? | 证明 Critic 的价值 |
| full（完整 6 Agent） | ? | ? | ? | 目标：显著最优 |

> 数字由实跑得出，我不预设结论。如果消融结果和预期不符，就如实写"某模块在该数据集上收益不显著"——
> **能讲清"为什么没提升"的候选人，比报喜的候选人可信得多。**

## 九、分阶段实施计划

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| **P0 契约** | 目录骨架、Pydantic 模型、DDL、节点接口签名、配置 | `python -c "import app"` 通过；模型单测通过 |
| **P1 数据层** | ETL 脚本、warehouse.sqlite、metric_catalog、schema_cards、fewshot_sql | 8 张表行数与源库一致；口径表 30 条 |
| **P2 编排引擎** | 状态图 Harness（节点/条件边/检查点/重试）、Provider（API+Stub）、trace | 3 个玩具节点跑通条件边 + 检查点恢复；trace 树正确 |
| **P3 六个 Agent** | 6 个 Agent + 安全执行层 | 单测覆盖每个 Agent；`PRAGMA query_only` 生效；恶意 SQL 全被拒 |
| **P4 服务与前端** | FastAPI + SSE、单页 UI、trace 页、eval 页 | 浏览器里问一句能出 SQL+表+图+结论 |
| **P5 评测** | 60 题评测集、eval runner、消融报告 | 四组配置跑完，产出对比表 |
| **P6 文档与简历** | README / ARCHITECTURE / AGENT_DESIGN / EVAL_REPORT / 简历条目 3 版 | 别人照 README 能 3 条命令跑起来 |

**多 Agent 协作方式（我这边）**：我担任架构与集成（写契约、定接口、最终验收），
下分 4 个执行 Agent 并行推进**互不重叠的目录**，最后由我集成分支并跑通全量测试。
你看到的是：每个阶段结束我给一次可验证的产物，而不是最后一次性丢一堆代码。
