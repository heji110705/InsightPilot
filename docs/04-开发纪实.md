# 开发纪实：数据坑与 8 个真实 bug

> 这份文档记录的是**定位过程**，不是结果。面试时被问"你踩过什么坑"，  
> 能讲清"现象 → 根因 → 修法 → 教训"的人，比报一堆技术名词的人可信。



---

## 一、数据层的三个坑（会直接毁掉结论的那种）

### 1. 评分是 0-10 分，不是 1-5 星

**现象**：按"好评率 = 4 星及以上占比"写口径，算出来 **99.7%**。  
一个电商图书库不可能有 99.7% 的好评率——这个数字本身就说明口径错了。

**根因**：源库 `books_rating.score` 实际取值 1.0~10.0（一位小数，88 个不同值），  
我凭经验假设成了 1-5 星。按 `score >= 4` 过滤，等于把 4 分以上全算成好评。

**修法**：口径改为 `score >= 8`，并把这条写进 `metrics.yml` 的 `caveats` 和表卡片：  
「`fact_rating.score` 是 0-10 分，不是 1-5 星；`dim_book.rating_avg` 同为 0-10 分」。

**教训**：**任何"看起来合理"的比率都要先算一遍基线**。99% 的好评率不是业务好，是口径错。  
语义层存在的意义就是让这种知识只写一次，而不是每次靠模型想起来。

### 2. 点击表里只有 55% 是点击

**现象**：`COUNT(*)` 统计"点击量"得到 9028，但把 event 拆开看是 `click 5001 + expose 4027`。  
直接计数会**虚高 80%**。

**根因**：`fact_click` 是一张**事件表**，不是点击表。字段名叫 `event` 而不是 `is_click`，  
已经是提示，但容易被"表名带 click"误导。

**修法**：所有点击类指标强制 `WHERE event = 'click'`，并写进 caveat。

**教训**：表名是命名，不是语义。语义要靠 `grain`（一行代表什么）来固定——  
所以每张表卡片都必须写 `grain`。

### 3. 视图 JOIN 出笛卡尔积，测试全绿但数字全错

**现象**：`v_book_overview` 四张事实表直接 LEFT JOIN 后 COUNT，  
`book_id=705` 的四个计数全都变成 **66924**（真实值 18/11/26/13）。  
行数仍是 250，所以"视图返回 250 行"的测试照样通过。

**根因**：1:N × 1:N × 1:N × 1:N 的乘积。`COUNT` 数的是连接后的行数，不是各自的行数。

**修法**：四张表先各自 `GROUP BY book_id` 预聚合成子查询，再 JOIN。  
修完 `705 → (18, 11, 26, 13)`，与逐表查询一致。

**教训**：**"测试通过"和"数字正确"是两件事**。这条也直接写进了 SQL 提示词：  
「多表关联时先按主键聚合成子查询再 JOIN，不要直接 JOIN 后 COUNT」。

## 二、我自己代码里的 5 个 bug

### 4. `4,202` 被读成两个数，导致"编造数字"误报

**现象**：自检报错「结论里出现了结果集没有的数字：202」。  
但结论里的 4,202 明明就是结果集里的值。

**根因**：千分位分隔符。正则 `-?\d+(?:\.\d+)?` 在 `4,202` 上匹配出 `4` 和 `202`。  
`4202` 在合法集合里，`202` 不在。

**修法**：校验前先归一化 `(?<=\d),(?=\d{3})` → 去掉逗号。

**教训**：**展示格式和判定格式必须分开**。给人看的千分位，不能进判定管道。

### 5. 自检器把统计代码自己算的派生值判定为"编造"

**现象**：趋势题的结论「合计 5,001，均值 2,500.5，首尾差 -3,403」被自检全部打回，  
因为合法集合只有结果集里的单元格 `[4202, 799]`。

**根因**：`collect_numbers` 只收原始单元格，但结论里的合计、均值、极差是**由这些单元格算出来的真话**。

**修法**：新增 `derived_numbers`——按列计算 sum / mean / max / min / 首尾差 / 极差并纳入合法集合；  
最终合法集合 = 原始单元格 ∪ 可重算的派生值。

**教训**：校验规则要区分"无法追溯的数字"和"可重算的数字"。  
过严的校验会把正确结论也毙掉，最后只能关掉校验——那才是真的失控。

### 6. 分组列被注入两次

**现象**：`SELECT category AS 分类, category AS 分类, COUNT(*) ...`

**根因**：部分指标模板（如 `publisher_book_cnt`）已经把分组列写进 `SELECT`，  
我的"按需前置分组列"逻辑又插了一次。

**修法**：注入前检查 `SELECT` 段是否已含该列。

**教训**：**模板和代码的职责边界要划清**。模板负责"算什么"，代码负责"按什么分组"，  
两边都自认为该管分组就会撞车。

### 7. `metrics[0]` 吞掉了所有问题（这一条最伤）

**现象**：首轮评测 EX 只有 **8.3%**。抽查发现"收藏最多的书"被执行成 `COUNT(*) FROM fact_shelf`，  
"评论转化率"返回 89.42%（真值 73.39%），"多少位作者"走错表得 197（真值 184）。

**根因**：`TemplateInferencer` 直接取检索结果的第一条指标，而不是"与问题最匹配的那条"。  
而指标目录里第一条是"书籍数"，于是**每个问题都变成了数书**。

**修法**：改为按"指标名/别名在问题中的最长匹配"选择，未匹配才回退到第一条。  
修完 EX 从 8.3% → **18.3%**，T2（分组排序）从 0% → 40%。

**教训**：**"有排序"不等于"选对了"**。检索给出了一个有序列表，  
但下游如果不做二次校验就用第一条，等于把排序当成了答案。

### 8. 上限被守卫提前压掉，`truncated` 永远是 False

**现象**：结果被截断时，前端从不显示"已截断"提示。

**根因**：`guard` 已把 SQL 的 LIMIT 压到 `row_limit`，`repo` 再 `fetchmany(row_limit + 1)`  
永远取不到第 N+1 行，溢出判定失效。

**修法**：`GuardResult` 增加 `capped` 标记，`repo` 用 `overflow or (capped and 取满)` 判定。  
（这个 bug 是分工时由数据安全模块的负责人发现的，我原本没意识到两层限制会互相掩盖。）

**教训**：**纵深防御会掩盖信号**。四层防护是好事，但每层都要把"我做了什么"上报给上层。

## 三、两处我拒绝做的事

1. **没有为了让评测好看而改 gold 集**。评测 Agent 发现 Q57 的 gold SQL 只过滤了点击、没过滤收藏，  
   与题面"收藏和点击都很少"不完全一致。我选择**记录在报告里、不改数据**——  
   改了 gold 就等于自己出题自己改答案。
2. **没有伪造 LLM 评测数字**。当前报告明确写着"规则基线，不代表 LLM 模式"，  
   README 的能力边界表里也写"LLM 模式待配 Key 后补测，当前不声称模型效果"。  
   拿不到的数字就写拿不到，这比一个漂亮但站不住的 65% 安全得多。

## 四、如果重做一遍，会改什么

| 现在         | 重做会怎样                                          |
| ---------- | ---------------------------------------------- |
| 语义层手写 YAML | 保留。但会增加一个"口径单测"：每个指标配 1 条断言 SQL，口径改错立刻红        |
| 规则基线靠关键词表  | 会做成"模板 + 少样本检索"的混合，而不是纯关键词，避免维护一张越来越长的别名表      |
| 60 题评测集    | 会拆成 dev/test 两半，避免调规则时把 test 也调了（现在是同一批）       |
| 单进程 SQLite | 数据量再大一个数量级就要换 DuckDB/Postgres，`repo` 的接口已经隔离好了 |

## 五、接了真实模型之后暴露的问题：降级是静默的

配 `.env` 切到 `IP_LLM_MODE=api` 之后，先用一条问题试跑，结果**看起来完全正常**：  
`status=ok`、SQL 正确、链路七个节点全走完。但接口实际返回的是 401  
（`Your api key: ****b701 is invalid`）。

原因在 `LLMInferencer`：它在模型报错时会把异常吞掉、回退到 `TemplateInferencer`，  
只往 `self.stats["sql_fallback"]` 加一。这个设计本身是对的——线上不该因为模型抖一下  
就整站不可用；**但它让"模型没答上"和"模型答对了"在返回值上长得一模一样**。

如果那时直接跑 60 题消融，会得到一份标着 `mode=api`、实际 100% 由规则模板答出的报告。  
数字是真的（确实是跑出来的），归因是假的，而且从报告上完全看不出来。  
这比不跑评测糟糕得多。

改了两处：

1. `app/eval/runner.py` 增 `_degradation()`：每轮把 `sql_fallback / intent_fallback /
   insight_fallback` 抬到指标层，`sql_fallback` 占比 ≥ 50% 或意图全量回退即判 `degraded`。
2. `scripts/run_eval.py` 在**写文件之前**检查：任一配置 degraded 就返回退出码 2，  
   并放弃写 `docs/eval_results.json` 与报告——宁可什么都不产出，也不覆盖上一份可信结果。

顺带修掉一个同源问题：`build_deps(force_template=True)` 原先只把推理器换成模板，  
`settings` 仍报 `api`，导致 `/api/health` 对外宣称在用模型、实际跑模板。  
现在强制模板时会把 settings 一起降级（`llm_mode="stub"`、清空 key）。

验证方式：用当前这个无效 Key 跑 `--limit 3 --mode auto`，确实返回退出码 2、  
`docs/` 下两个文件时间戳未变、219 个测试仍全绿。

> 面试可讲的一句话：**降级策略必须和观测绑定**。只做 fallback 不做计量，  
> 系统会在最需要信任它的时候安静地骗你。

## 六、第一次跑真实模型，把我自己的消融结论推翻了

接上有效的 `sk-` 密钥后，先跑四组：full 41.7%、no_critic **45.0%**、no_schema 38.3%、single 40.0%。

两个地方不对。

**第一，no_critic 比 full 高。** 而 Critic 只写结论措辞、不碰 SQL，  
从代码路径上说它**不可能**影响结果集等价。我去比对两组的逐题 SQL，发现 60 题里只有 25 题  
文本完全一致——`temperature=0` 并没有让生成变成确定性的（MoE 路由与服务端批处理会带噪声）。

**第二，这意味着组间差距可能是噪声。** 于是我把 full 原样重跑一遍：**45.0%**。  
同一个配置，两次差 2 道题、3.3 个百分点，和四组之间的差距同量级。

补跑另外三组各一次后，两轮均值是：

| 配置        | 两轮            | 均值    |
| --------- | ------------- | ----- |
| full      | 41.7% / 45.0% | 43.3% |
| no_critic | 45.0% / 43.3% | 44.2% |
| no_schema | 38.3% / 40.0% | 39.2% |
| single    | 40.0% / 38.3% | 39.2% |

结论必须改口：**这张表不能证明「多 Agent 编排带来准确率提升」。**  
组间极差 5.0pp，重复波动 3.3pp，每配置 n=2，说什么都虚。  
能说的只有：去掉语义层或退化成单 Agent 各掉约 4 个点（方向对、不显著），  
**去掉 Critic 反而高 0.9 个点（噪声内，等于没测出收益）**。

于是加了 `scripts/repeatability.py`，把每个配置的多次运行汇总成「均值 + 极差 + 逐题翻转表」，  
产出 `docs/03b-重复性检验.md`；并在 `docs/03` 抬头加了一条硬提示：  
单次运行表里小于 3pp 的差异不得解释。README 与简历素材里的说法全部同步改写——  
原来那句「多 Agent 提升了 X%」被我自己删掉了。

**这一节是整份纪实里我最想让人看的部分**：一个方案最容易骗人的时刻，不是它跑不通，  
而是它跑通了、数字还变好了，而你刚好没做重复实验。

## 七、顺带修掉的三个 bug（都在报告层）

1. **无 `full` 时渲染崩溃**：`results.get("full", metrics[0])["metrics"]` 在只跑三组时  
   把已经拆包的 metrics 又取了一次 `["metrics"]`，直接 KeyError。是补跑第二轮才暴露的。
2. **模式串词**：api 模式下报告仍可能写出「这不是 LLM 模式：本次为 api 规则基线」——  
   结论段没走模式分支。已按模式分叉，并加三条测试守住。
3. **组数与变体名写死**：「四组配置」在只跑三组时是错的；无 `full` 时把 `no_critic`  
   称作 full。改为按实际组数与 `variant` 取词。

## 八、我以为的靶子，其实是症状

这一节记录一次判断失误，以及它怎么被证伪的。它比前面七节都更接近真实开发的样子。

### 8.1 错误的起点

第一轮评测跑完，我把失败构成写进了 README：

> 35 个失败里 26 个是「列数不同」（模型多给了未被问到的列），
> 前者是可以靠提示词约束收掉的，说明 43.3% 更多是提示词问题而非模型能力上限。

这句话读起来很顺，也很有说服力。问题在于它是**从 diff 文本的首行推出来的**，
而 diff 只告诉我"列数不同"，没告诉我"因为什么不同"。

### 8.2 按错误结论去改，然后被打脸

照着这个结论，我在提示词里加了一条"只 SELECT 必需的列，不要把分子分母一起给"。
跑完 60 题：

| | EX | 覆盖一致 | 平均列数 |
|---|---|---|---|
| 改之前 | 41.7% | 48.3% | 2.93 |
| 加了投影约束 | 41.7% | 41.7% | 2.00 |

列数确实从 2.93 压到 2.00（省了 32%），**但正确率一点没动，覆盖一致反而掉了**。
如果只看 EX，会得出"这个改动无效但无害"的结论——那是错的，它有害：它把
"好评率"这类题的分子分母删了，用户失去了核对能力。

### 8.3 转折：把"列覆盖"做成指标，才看清 26 个里是什么

问题出在判定太刚性：列数不相等就直接判错，不区分"多给"和"少给"。于是我加了
`compare_covering`——只要金标准的每一列都能在预测里按值找到、行不错位，就算覆盖一致。

拿它离线重算旧结果，第一个数字就把我之前的说法推翻了：

- EX 41.7%（25/60）
- 覆盖一致 48.3%（29/60）
- **两者只差 4 题**

也就是说，26 个"列数不同"里，**只有 4 个是真正的投影问题**。剩下 22 个虽然列数也错，
但取值或行数同样错——把列修对了也还是错。

继续按方向拆：**15 个是多给，10 个是少给，1 个是 0 列（执行失败）**。
"模型老爱多给列"这个说法，连方向都不对。

### 8.4 再往下挖，发现问题在考卷上

逐题看这 26 个 case 的 SQL，发现了更根本的东西：**8 道题的题面问"哪一本"（单数），
金标准却返回 5 行。**

> Q51「最受欢迎的是哪本书？」金标准：`LIMIT 5`，3 列
> 模型：`LIMIT 1`，2 列

这不是模型答错，是题目本身没有唯一答案。同一批还有 Q52/Q53/Q54/Q55/Q56/Q58/Q29。
T6 全灭（0%）里，有 6 题是这个原因。

到这一步我才明白：**"列数不同"不是一个失败原因，是一种症状。** 它背后至少有四种病：
投影没收住、题面与金标准矛盾、金标准带展示性列、以及"值本来就错了、只是顺带列数也不对"。
按症状去做优化，等于按发烧去治肺炎。

### 8.5 修的过程中又踩了一个坑

把输出约定搬进 `defaults.yml` 之后，我写了"排名类默认 LIMIT 10"。听起来合理，
实际把 Q15/Q20/Q24 这类**"各个分类分别多少"的全量分组题**也砍成了 10 行——
金标准是 12 个分类，模型只给 10 个。

这是典型的"修一个引一个"：规则写得太粗，把"排名取前 N"和"列全部分组"当成了一回事。
改法是把两类分开写清楚：

> 排名 / 榜单类默认 `LIMIT 10`；**全量分组类不要加 LIMIT**，砍掉两组就不是分布了。

### 8.6 学到的东西

1. **diff 的第一行不是归因。** "列数不同"要展开成"谁多谁少、值对不对"，才能当结论用。
2. **判定指标决定了你能看见什么。** 只有严格 EX 时，我看不见"多给一列"和"算错"的区别；
   加上覆盖判定，26 个 case 才裂成 4 + 22。
3. **评测集本身会错。** 8 道单复数矛盾的题，在 60 题里占 13%，足以让任何提示词优化
   看起来"没效果"。先审考卷，再调模型。
4. **改规则要能说出它不适用于什么。** "默认 10 行"这条规则如果没有写清"全量分组除外"，
   它就会在另一个方向制造新错误。

最终两轮的结果是：EX 从 43.3% 到 50.0%（均值），覆盖一致 57.5%。（中间某一轮曾测到
50.9%，差 0.9 个百分点、不到一题，落在噪声带内，这里统一引用最终两轮均值。）但按 8.3 的
拆法，这个提升里有多少来自"题目变清楚"、多少来自"系统变强"，我没有做单因素实验，
所以不下因果结论——这一点和第六节的结论保持一致：**能说清的事说清，说不清的不编。**
