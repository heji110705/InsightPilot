# InsightPilot 评测报告（结果集等价）

> 判定口径：列数相同、列名不比较、行序不比较（多重集）、数值 1e-6 相对容差、字符串去首尾空白且大小写敏感、None 与空串不等。
> 所有指标由 `scripts/run_eval.py` 实跑写入 `docs/eval_results.json` 后渲染，没有手填值；第 5.2 节标注为直接 SQL 抽检的数字除外。

## 1. 结论

四组配置在 60 题上的 EX 分别为 full 18.3%、no_critic 18.3%、no_schema 16.7%、single 16.7%；最高 18.3%（full/no_critic），最低 16.7%（no_schema/single），极差 1.7 个百分点。

full 比 no_schema 高 1.7 个百分点（18.3% vs 16.7%），差异全部来自 SchemaLinker 是否按相关性挑指标；而 no_critic 与 full 同分、`attempts>1` 的题数为 0，说明模板模式下 Critic 与重试没有可观测收益。

这不是 LLM 模式：本次为 stub/`template` 规则基线，绝对数字只说明模板路径的能力上限，不能当作模型效果；原因见第 5 节。

## 5. 低分排查记录

EX 低于 0.3 的防呆线，先排除评测框架本身的问题，结论如下（全部可复核）：

1. **不是缓存命中**：每题都显式 `use_cache=False`，本次指标里 `cache_hits=0`，且 `report.path` 均以 `intake` 开头。
2. **不是 deps 复用串题**：同一 variant 复用 deps 只共享只读的 repo / retriever / DimIndex，`TurnState` 每题新建；重复跑同一题结果稳定。
3. **不是执行链路坏了**：full 的 49 题失败中，`wrong` 48 题（SQL 成功执行但结果不等）、`failed` 0 题、`clarify` 1 题；绝大多数是「能跑但不对」。

真正的根因在规则模板推理器 `TemplateInferencer`，与评测框架无关：

- **只信 Top-1 指标**：`_metric_sql` 直接取 `context.metrics[0]`，不校验该指标是否回答当前问题。Q35「每天有多少人来逛」的 Top-1 是「收藏数」，生成的 SQL 变成 `COUNT(*) FROM fact_shelf`；Q42「整体好评率」的 Top-1 是「正向评论占比」，落到了 `fact_comment`（89.42% vs 73.39%）。更隐蔽的是口径错位：Q02「涉及多少位作者」的 Top-1「作者数」把口径定在 `dim_author`（197），而 gold 按 `dim_book` 去重（184）；Q04「多少人在打分」的 Top-1 是「评分数」，直接 `COUNT(*)` 出 4202，而 gold 要去重用户（101）。
- **结构解析覆盖不足**：`detect_group` 只认「各/按/每/分别/分组」，「哪个分类」「哪几年」不触发 GROUP BY；`detect_limit` 只认阿拉伯数字，「前十家」「前五名」「八年」都拿不到 LIMIT。Q11 因此退化成全表计数。
- **固定 4 列投影**：命中实体类问题时模板固定输出「书名/作者/分类/指标」四列，而 gold 多为 2 列（如 Q21 只要书名+评论数），列数不同直接判不等，哪怕 Top-10 的书是对的。
- **单表模板表达不了 JOIN/窗口/子查询**：60 题里大量 T3/T4/T5/T6 需要多表预聚合、`OVER`、`INTERSECT`，指标模板只有单表聚合，结构上不可能等价。

`no_schema` / `single` 的额外塌陷：`linker_wide` 把指标目录前 8 条原样塞进上下文，`metrics[0]` 恒为「书籍数」，于是几乎每题都变成 `COUNT(*) FROM dim_book`，EX 降到 16.7%。这正好反证了相关性排序的价值，但也说明该消融在模板模式下分辨的是「指标选择」而不是「LLM 的 schema linking 能力」。

消融也不是逐题单调的：Q03 在 full 下 Top-1 命中「出版社书籍数」（2 列），反而 no_schema 固定取「书籍数」加维度过滤（1 列）答对了。5 vs 2 的组间差距里既有召回收益，也有召回选错指标的噪声，不能简化成「每个模块都正向」。

Critic 与重试为何没有差异：模板 SQL 是确定性的，执行错误几乎为 0，`attempts>1` 的题数为 0；`rule_critique` 只校验结论里的数字是否能被结果集支撑，而模板结论本身由结果集算出，因而总是通过。换句话说，**在规则基线上这两个模块没有可发挥的场景，不能据此判断它们在 LLM 模式下无效**。

### 5.1 引擎侧代码缺陷（只报告，不修改）

- **重复投影列**：`TemplateInferencer._metric_sql` 在指标模板已经自带分组列时，仍执行 `sql.replace("SELECT ", f"SELECT {column} AS {alias}, ", 1)`，产出 `SELECT category AS 分类, category AS 分类, COUNT(*) AS 书籍数 ...`。full / no_critic 各有 4 题命中（Q13、Q20、Q24、Q43），列名重复且第二列语义错误。本次不修：交付范围限定在评测文件，改动推理器会让四组基线数字失去可比性。修掉它也不会直接让这 4 题通过（Q13 还缺 `price > 1` 过滤、Q43 缺占比列、Q24 缺 JOIN），但失败原因会从「重复列」回到真实的 SQL 结构差异。

### 5.2 gold 口径观察（只报告，不修改）

- **Q57**：问题说「收藏和点击都很少」，但 gold SQL 只过滤 `click_cnt < 20`，没有给 `shelf_cnt` 设阈值（该子集收藏数实际 2–21），`note` 也只写了 click 阈值。若按题面严格执行，结果集会不同。
- **Q22 vs Q51**：前者「被收藏最多」按收藏次数（`COUNT(shelf_id)`），后者「最受欢迎」按去重收藏人数；两种口径都写在 note 里，属有意设计，但结果集等价的评测无法区分「口径选错但数字碰巧相同」的情况。
- 其余 note 中的关键数字已抽检并与库内一致（以下数字来自直接对 `warehouse.sqlite` 执行校验 SQL，不是评测脚本产物）：评分总数 4202、书目作者 184 / 作者档案 197、整体好评率 73.39%、精装 63 本、豆瓣更高 196 本、Q57 命中 25 本、Q52 第一名《少年凯歌》9.7/17 人、Q54 两种口径第一名均为「哲学宗教」。

## 6. 局限性声明

- **本报告为规则基线结果**：运行在 template 模式（无 LLM Provider，inferencer=`template`），不代表 LLM 模式表现；接入模型后必须重跑，不能引用本表数字。
- **数据快照极窄**：仓库只有 2026-10-18 与 2026-11-01 两天（且都是周日），T4 时间类题目没有「上个月/按周趋势」的真实跨度，区分度有限；任何关于时间分析的结论都不具备统计意义。
- **样本量小**：60 题、每题权重 1.67%，百分比的 95% 置信区间约 ±12 个百分点；两组相差 1–2 题（1.7–3.3 个百分点）不能说明模块优劣。
- **结果集等价 ≠ 语义正确**：列名与行序不参与比较，同一数字的不同口径（如收藏次数 vs 收藏人数）可能都被判为「等价」；评测只能证明「算出了同一张表」，不能证明「选对了业务口径」。
