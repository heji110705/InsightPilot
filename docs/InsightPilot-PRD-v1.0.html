InsightPilot · 自助问数

作者 何志伟　｜　角色 产品 + 实现（0→1 独立完成）　｜　更新时间 2026.11　｜　状态 V1 已交付

一句话：让不会写 SQL 的业务同学用中文提问就能自己拿到数字，并且每个数字都能自证（附 SQL、结果集、口径说明）。

1背景与要解决的问题

中小电商 / 内容团队里，业务同学要一个数字（"昨天精装书卖了几本""各出版社均价差多少"），流程是：提需求 → 找数据同学排期 → 等一条 SQL → 拿到一张没有上下文的表。一次一天起，而且拿到数字的人无法确认它是怎么算出来的。买了 BI 的团队卡在另一头：报表配好了，问题一变还得找人重新配。

真正卡住的不是"查得到"，是查得快 + 敢用：口径要一致、数字要能复核、答不了的时候要说答不了。

2目标用户与场景

角色典型问题现在怎么做期望
运营昨天各分类销量多少？哪个掉了？提需求、等排期，一天起1 分钟内自助拿到，可自己追问
分析精装比平装贵多少，按出版社拆自己写 SQL，口径每次重算一遍复用已定义口径，结果可直接引用
管理层"均价"到底含不含赠品？问三个人得到三个答案口径可查，答案自带脚注

3目标与非目标（明确不做的事）

目标：单轮问数答对率 ≥ 50%（60 题基线）｜答案可复核率 100%（每条答案附 SQL 与结果集）｜p50 ≤ 8s｜单题成本 ≤ ¥0.01。

非目标（本期不做）：报表配置与定时订阅、复杂多表建模、图表自由编辑、多租户与行级权限、移动端。理由是这五项都会把产品从"回答问题"拖向"配置系统"，而后者已有成熟工具。

4主流程

提问›意图识别›口径澄清›语义层三路召回›生成 SQL›安全校验 / 执行›结果解读与选图›结论自检

两条反馈回路：执行失败 → 错误信息 + 原 SQL + 相关表卡片回灌重写（最多 3 次）；结论自检不通过 → 打回重算。全过程落 trace，可逐节点回看。

5三个关键产品决策

决策做法为什么这样取舍
D1 模糊词不追问"最近 / 最好 / 热门"一律采用显式默认口径并标注；只有涉及不同表、会算错数时才回问。每次追问都是一次打断，连问三次用户就走了；宁可给一个标注了口径的答案，让用户自己能纠正。
D2 数字不许模型口述结论句必须绑定结果集里的具体值，由代码计算；对不上就打回。用户信不信这个答案，取决于能不能复核。一个编出来的数字比没有数字更糟。
D3 答不了就说答不了样本量 < 30 条时显式提示"仅供参考"；数据不支持时直接拒绝并说明缺什么。错答的代价远高于不答。产品可信度一旦被一次错答击穿，用户就不会再用第二次。

6验收指标与版本对比方法

层级指标当前值判定口径
北极星单轮问数答对率50.0%（基线 18.3%）结果集等价：列名/行序无关，1e-6 容差
护栏 1列覆盖57.5%答案是否覆盖了应给的维度，避免"对了但没用"
护栏 2响应与性价比p50 5.7s ／ ¥0.005 每问同问命中缓存 0.04s
护栏 3安全54 条用例全通过写操作 / ATTACH / PRAGMA / 系统表一律拦截

版本对比方法：60 题 × 4 种策略配置 × 每配置 2 轮，两轮波动 0–3.4pp；差异小于波动幅度的改动不算改进。这条规则是为了防止"改一版跑一次就宣布提升"。

7能力边界（做不到的部分，写在产品里）

  • 趋势 / 同比环比答不了：dim_date 仅 15 行、事实表日期几乎单值，算不出时间序列；产品明确回"数据不支持"，而不是画一条错曲线。
  • 仅支持文本提问：不支持截图、表格上传、语音（多模态未接入）。
  • 无权限体系：只适合单团队内部使用，不支持多租户与行级权限，接入企业环境前必须补。

8迭代计划

V1（已交付）：单轮问数、多轮追问、口径默认与脚注、评测页与消融对比、全链路 trace、安全沙箱。

V2 候选（按预期影响排序）：① 口径收藏与复用 → ② 带 SQL 与脚注的结果分享链接 → ③ 失败问题回流语义层（答错的题变成新表卡片）→ ④ 多轮澄清 → ⑤ 权限与多租户。
