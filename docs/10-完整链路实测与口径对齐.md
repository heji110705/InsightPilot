# 10 · 完整链路实测与口径对齐

> 起因：原型里「英国作家有几本」答不了、库里明明有 30 本。上一轮我给原型加了一层实体模板，
> 但那是**针对单个问题打补丁**。这份记录回答两件事：
> ① 其余问题必须在本机把**完整链路**（语义层 → LangGraph 七节点 → SQL 守卫 → 真库）跑一遍，
> 用链路输出反查原型；
> ② 到底能不能不跑完整链路、直接对任意问题作答——能到什么程度、边界在哪。

## 3 四处对不上，逐个说根因

### 3.1 「英国作家」= 0：语义层没写国别规则，模型只能猜

真值：`[英]` 前缀 24 位作家、30 本书。链路写的是 `a.life LIKE '%英国%'`。

- `life` 在表卡片里的说明是"生卒年自由文本"，存的是 `1903-1950` 这类值，不可能含"英国"。
- 但这条 SQL **语法合法、列名合法、守卫全部通过**，没有任何一层会拦它。结果返回 0，分析师照样写出
  "英国作家对应的书籍数为 0"，批评节点也没意见（它只看结果和问题是否矛盾，不看字段选得对不对）。
- 根因不在模型，在语义层：`dim_author` 只有 `author_id / name / life` 三列，**没有国籍字段**，
  国别信息藏在 `name` 的方括号前缀里（`[英] J·K·罗琳`、`[美] 傅高义`），而表卡片只写了
  `含"(清)曹雪芹"这类前缀`，没提国别。模型手上没有这条信息，只能编一个看起来最像的字段。

> 这类错误最贵：不是报错，是一个**看起来正常的 0**。面试里如果被问"你怎么保证模型不瞎编字段"，
> 这条就是最好的反面教材——守卫能拦语法和越权，拦不住语义。

### 3.2 精装 63 还是 66：口径没定，两种都对

```
binding 实际取值：平装 181 / 精装 63 / 软精装 1 / 精装16开 1 / 平裝 32开 1 / 平装-精装 1 / 套装 1 / 空 1
binding = '精装'        → 63
binding LIKE '%精装%'   → 66（多出软精装、精装16开、平装/精装）
```

原型的脚注写的是"精确匹配"，链路写的是 `LIKE`，两个数字都出现在简历材料里过一次。这不是 bug，
是**口径没有单点定义**：同一句话有两条合法解释，谁先跑出来谁就算对。处理方式不是二选一，
而是把它写进语义层的 caveat，并要求结论句必须带上是哪一种。

### 3.3 差价 20.29 还是 18.65：原型违反了语义层自己写的规则

语义层 `dim_book.caveats` 第一条明写：**算均价前先 `WHERE price > 1`**（有 0.2 元这类脏值和 1 条 NULL）。

- 原型：没剔 → 平装 181 本均价 40.72 → 差价 **20.29**
- 链路：剔了 → 平装 173 本均价 42.35 → 差价 **18.65**

链路对、原型错。更难看的是：这个 20.29 是我上一轮亲手写进原型的，还配了一句"不剔除极值"的脚注——
**脚注在为一个违反自己规则的数字辩护**。已经改回 18.65，并把两个数一起写进脚注（差 1.6 元，
但"两个数都能自圆其说"正是口径必须写清的理由）。

### 3.4 「骑行」= 0：0 行不等于 0

SQL 层完全合法，返回 0。但 0 有两种含义：**有这个东西、只是没有数据**，和**根本没有这个东西**。
链路当时把后者也输出成前者：`status=ok`、headline「骑行对应的书籍数为 0」。

改法是加一层反向校验（`app/db/domain.py`）：答案已经生成后，把 `WHERE` 里的等值字面量拿去维表里比对，
查无此项就把结论改成「这个 0 是空集，不是结论」，并给出该列真实取值。只处理
`col = '字面量'` 与 `col LIKE '%字面量%'` 两种形态，`IN`/`OR`/带前后缀的 LIKE 一律放过——
**判不准就不提示，不能把正常的 0 说成错误**。

### 3.5 我自己埋的坑：NULL 被当成 0

上一轮生成原型实体表时，均价是这么算的：`d['sum'] += (r['price'] or 0)`。NULL 被当成 0，
科学科普从 43.20 变成 34.56，卡片和实体表各显示一个数。这次用 SQL 重算（`AVG` 天然忽略 NULL）
才发现。教训：**任何"我在 Python 里复算一遍聚合"的地方，都要和 SQL 对一次数**。

## 6 能不能不走完整链路，直接回答任意问题？

**结论：不能对"任意"问题回答。能在一个很窄的语法闭集里回答，且必须同时满足四个条件。**

### 6.1 现在这张实体表能做什么

原型里内联了一张由 `warehouse.sqlite` 实查生成的实体表：186 位作者及其书目、12 个分类的本数与均价、
8 种装帧取值、24 个国别前缀。匹配规则只有一条：

```
实体 × 计数   →   COUNT(*) WHERE <维度> = <实体>
```

（`多少本 / 几本` 命中；句子里出现 `平均/价格/评分/评论/销量/最高/占比/趋势` 一律不接。）

### 6.2 适用条件：四条同时成立，缺一不可

1. **问题能落到闭集模板**：目前只有一个模板（实体 × 计数）。模板里唯一的槽位是"实体"，
   所以只有一种句式能被正确解析。
2. **实体在表里**：作者名（含国别前缀归一）、分类名、装帧值、国别名。不在表里就答不了——
   这也是「骑行」在原型里直接"不猜"的原因。
3. **数据不变**：实体表是数据快照。库一改，表就得重建（生成脚本在 `_work/`，不是手抄）。
4. **只要"数 + 明细"**：不需要解释为什么、不需要比较、不需要多轮。

### 6.3 限制：为什么不能推广到"任意问题"

| 限制 | 具体表现 | 举例 |
|---|---|---|
| 组合爆炸 | 每加一个过滤条件就要加一个模板 | 「英国作家里评分 > 9 的有几本」不接 |
| 聚合口径 | 均价/占比/差值要先定清洗规则与分母 | 「精装比平装贵多少」在原型里必须写死 `price>1` |
| 脏值归一 | 同一实体多种写法，表里不合并就答错 | `意` 与 `意大利` 不合并 → 8 本 + 1 本 |
| NULL 语义 | Python 复算与 SQL 的 `AVG` 不一致 | 把 NULL 当 0 → 34.56（真值 43.20） |
| 时间窗口 | 需要判断日期维度是否覆盖 | `dim_date` 只有 15 天，"上个月"无从谈起 |
| 多轮指代 | 需要改写与上下文 | 「那平装呢」 |
| 无新 SQL 能力 | 模板拼 SQL，不是生成 SQL | 任何没预置的分析都做不了 |

一句话：**模板把"正确率"换成了"覆盖率"**。它永远不会给你一个错数（不命中就明说答不了），
但也永远只会答那一类问题。

### 6.4 什么时候必须走完整链路

出现下面任意一个词，就一定得跑链路：`平均 / 排名 / 占比 / 差 / 趋势 / 同比 / 环比 / 对比 /
最 / 前 N / 多条件 / 否定 / 时间范围 / 指代`。

### 6.5 三条路线对比（原型现在走的是第三条）

| 路线 | 成本 | 覆盖 | 风险 |
|---|---|---|---|
| A 纯模板（实时算） | 最低，页面内 JS 直接答 | 只覆盖闭集模板 | 口径写死，改库要重建 |
| B 离线物化（跑一次链路，把答案存成静态数据） | 中，每题约 6 秒 + 人工确认 | 问题集固定时 100% 正确 | 数字会过期，必须标生成时间与 SQL |
| C 现场跑完整链路 | 高，需要 Python 环境 + LLM Key | 任意问题（受语义层约束） | 慢（~6s）、要联网、要看 Key |

原型 = A + B：6 条示例是 B（链路跑过、数字与 SQL 一起抄下来的），实体维度是 A（模板实时算，
但数据来自同一个库）。所以**原型里每一个数字都能追到一条 SQL**，这是它敢放在公网上的原因。

### 6.6 面试怎么说（30 秒版）

> 问：这东西不接模型也能答，那模型是多余的吗？
>
> 答：不是。闭集能枚举的问题（某作者/某分类有几本）用模板答，成本低、永远不会错，但只覆盖一小撮；
> 一旦出现"平均、排名、占比、对比"，模板就要为每种组合写死口径，写不完也维护不了，这时候必须让模型
> 生成 SQL。所以我把两者做成一条链路的两端：模板负责"确定的"，链路负责"要算的"，中间用同一份语义层
> 保证口径一致——精装是 63 还是 66、均价剔不剔脏值，这些问题在两个端上必须是同一个答案。
